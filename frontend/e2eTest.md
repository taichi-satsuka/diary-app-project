# E2E test

## E2Eテストとは
- End-to-Endテスト
- アプリケーション全体が**入り口から出口まで（END → END）**期待通りに動くかを確認するテスト

## 目的
### 1. **ユーザー体験の保証**
- Uiや画面遷移、入力や出力が**期待通り動くか**をユーザー視点で確認
### 2. **コンポーネント間の連携の検証**
- 単体では正しく動く機能でも、連携すると不具合が出ることもある。e2eテストでは**アプリ全体の動作の繋がり**を確認
### 3. **本番に近い環境での検証**
- 環境設定、ネットワーク、外部APIなどを含め、**運用環境に近い状態**でテストできるため、実運用のトラブルを防ぐ

## 実際の例
Web アプリの e2e テスト例：

1. ブラウザを自動で起動
2. ログインページにアクセス
3. ユーザー名・パスワードを入力
4. ログインボタンをクリック
5. ダッシュボード画面が表示されたか確認
6. 一覧のデータがロードされるか確認
7. ログアウト操作の動作確認

実際のユーザー操作そのものを再現

## e2eテストの特徴（メリット・デメリット）
### メリット
- **ユーザー視点での品質保証ができる**
- **システム全体の問題を発見しやすい**
- UI, API, DBなどの構成要素の連携を確認できる
- 単体テストでは発見しにくいバグを検知できる

### デメリット
- 実行に時間がかかる（プラウザ起動など）
- テストが不安定になりやすい（ネットワークなどの影響）
- 作成、保守のコストが高い
- 失敗時の原因特定が難しい（どの層のバグか判断しにくい）

## 他のテストとの違い
| テスト種類 | テスト範囲 | 目的 |
| -------- | --------- | -----|
| 単体テスト（Unit test）| 関数・クラスなど単一の要素 | 個々のロジックが正しく動くか |
| 結合テスト（Integration test）| 複数モジュールの連携 | インターフェースが正しく連携するか |
| e2eテスト（System/Acceptance test）| システム全体 | ユーザーが使ったときに正しく動作するか |

## 主なツール
- webアプリ用
    - Playwright（高速・安定・モダン）
    - Cypress（フロントエンド寄り、扱いやすい）
    - Selenium（歴史が長く、さまざまなプラウザに対応）
    - Puppetter（Chrome/Chronium専用）
- mobile専用
    - Appium
    - Detox

## e2eテストが効果的になる場面
- リリース前の総合的な確認
- 複雑なユーザーフロー（e.g., カート→決済→注文履歴）の検証
- ログイン・権限管理・重要導線のチェック
- システムの大きな改修後の回帰テスト


## e2eテストはシナリオベース
### シナリオベースに留めるべき理由

#### 1. e2eテストは重い
- ブラウザ起動、画面遷移、ネットワーク処理などが多く、**実行が遅い**。
- 大量に作ると CI/CD が重くなる。

#### 2. 壊れやすい（フレークしやすい）
- 非同期処理やネットワーク遅延で簡単に失敗する。
- テストが多いほど保守コストが急増。

#### 3. 失敗時の原因特定が難しい
- UIか？APIか？DBか？ネットワークか？
- 範囲が広いほどデバッグが複雑になる。

#### 4. 細部のカバレッジには向かない
- 全画面・全パターンを e2e で網羅するのは非現実的。
- 細かい部分は他のテストに任せるべき。


### “やるべき”と“やらないべき”の境界

#### e2e でやるべき（主要シナリオ）
- ログインフロー
- ユーザー登録 → メール認証 → ログイン
- カート → 支払い → 注文完了
- データ作成 → 一覧反映
- パスワード変更

#### e2e でやるべきでない（細かすぎる）
- 全てのバリデーションチェック  
- UIコンポーネントの挙動（モーダル開閉など）
- API の成功/失敗パターン全網羅
- 文言やデザインの細かい一致

&rarr; これらは **unit / integration / component test の領域**



| state | 説明 | 使う場面 |
|------|------------|--------|
| attached | DOMに要素が追加されている状態。<br>表示されているかは関係ない。 | 非表示でも存在している必要がある場合。DOM操作したい時。<br>（例：inpoutに値を設定する前にフォームが存在するか確認）|
| visible | DOMにあり、かつ表示されている状態<br>（opacity:0 や display:none は不可視とみなされる）。 | ユーザー操作が必要なボタンやリンクなど、画面上で<br>クリックできることを保証したい場合 |
| hidden | DOMに存在しないか、display:none / visibility:hidden <br>/ opacity:0 の状態。 | ローディング終了待ちや、モーダルが閉じたか確認するとき |
| detached | DOMから削除されるのを待つ状態。 | 要素が完全に消えるのを確認したいとき |

## プラウザコンテキストとは
同じプラウザ内で独立した**仮想プラウザ**のこと
- ひとつのプラウザインスタンス（browser）の中に複数のコンテキストをを作れる
- コンテキストごとに Cookie, LocalStorate, SessionStorageは独立
- ページ（タブ）はコンテキストごとに作られる
```typescript
import { test } from '@playwright/test';

test("test", async ({ browser}) => {
    // コンテキストを作る
    const context = await browser.newContext();
    // 新しいページを作る
    const page = await context.newPage();

    // test処理記述

    // テスト終了時にクローズ
    await context.close()
});
```
これを行うと：
- そのコンテキストのCookieやLocalStorageは破棄される
- 次のテストで新しいコンテキストを作成すれば**完全にクリーンな状態からスタートできる**

## workersとは
同時に実行されるテストの数（並列実行数）
- workers = 1 → テストは1本ずつ順番に実行（直列）
- workers = 4 → 最大4本のテストが同時に実行（並列）


## E2Eシナリオ一覧

| 粒度 | シナリオ名 | 正常系 | 異常系 |
|------|------------|--------|--------|
| ユーザー認証 | ユーザー登録 | 必須項目入力で登録 → 自動ログイン | 必須項目未入力 → エラー表示、重複メール登録不可 |
| ユーザー認証 | ログイン/ログアウト | 登録済みアカウントでログイン → ホーム遷移 → ログアウト | 存在しないユーザー / パスワード誤入力でエラー表示 |
| プロフィール管理 | プロフィール編集 | ユーザー名・自己紹介文更新 → プロフィール画面反映 | 空文字や文字数超過 → エラー表示 |
| 日記操作 | 日記投稿 | タイトル・本文入力 → 全体公開 → ホーム画面に反映 | タイトル・本文未入力 → 投稿不可 |
| 日記操作 | 日記編集 | 自分の投稿を編集 → 内容更新 | - |
| 日記操作 | 日記削除 | 自分の投稿を削除 → 投稿一覧から消える | - |
| 投稿表示 | 投稿一覧表示 | 投稿者・タイトル・いいね数・日時が正しく表示、新しい順 | - |
| 投稿表示 | 日記詳細表示 | 投稿内容確認 → プロフィール遷移 → いいね・コメント操作可 | - |
| フォロー | フォロー/フォロー解除 | 未フォロー → フォロー成功、フォロワー数増加、一覧に反映<br>フォロー済み → 解除成功、フォロワー数減少 | - |
| いいね | いいね/いいね解除 | 未いいね → いいね成功、カウント増加<br>既いいね → 解除成功、カウント減少 | - |
| コメント | コメント投稿 | コメント入力 → 投稿 → 表示確認 | - |
| 自分関連 | 自分の投稿一覧表示 | 投稿一覧が正しく表示 → 詳細ページ遷移可能 | - |
| 自分関連 | 自分のいいねした投稿一覧表示 | いいねした投稿が一覧表示 → 詳細ページ遷移可能 | - |
